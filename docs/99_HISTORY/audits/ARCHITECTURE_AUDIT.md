# SUDARSHAN Architecture Audit Report

This report summarizes the architectural layout of the SUDARSHAN repository, capturing entrypoints, boundaries, dependencies, and execution paths across the entire system.

## 1. Directory Structure and Modules
*   **`backend/`**: Contains the API gateway and orchestrator (FastAPI). It manages user authentication, state persistence, analysis job queuing, and exposing REST endpoints for the frontend.
*   **`analysis-engine/`**: A standalone microservice (FastAPI). It manages and executes the actual analysis tools (APKTool, JADX, Androguard, Frida) and runs the dynamic sandbox logic.
*   **`frontend/`**: The React 18 Single Page Application (SPA) providing the analyst dashboard, served via Vite.
*   **`shared/sudarshan_core/`**: A core Python library shared between the backend and analysis-engine. It houses domain models, analyzers, AI agent planners, database storage abstractions, and configuration.
*   **`VIDE/` (banking-baseline-corpus-main)**: The Visual Impersonation Detection Engine baseline corpus, containing reference profiles and structures for banking applications.
*   **`deploy/`**: Contains Dockerfiles and deployment configurations (e.g., `Dockerfile.laya`).
*   **`scripts/`**: Utility scripts for database administration, baseline generation, testing scripts, and system health checks.
*   **`tests/`**: Contains comprehensive unit, integration, security, dynamic, and regression tests.
*   **`tools/`**: Stores host-side cached binaries like the frida-server.
*   **`docs/`**: Documentation including architectural and detection audits.

## 2. Entrypoints
*   **Frontend (Analyst Dashboard)**: `frontend/src/main.tsx` (served via Vite on port 5173).
*   **Backend (Gateway Orchestrator)**: `backend/app/main.py` (FastAPI app on port 8000). Provides APIs for auth, cases, reporting, batch scans, and intelligence.
*   **Analysis Engine (Worker)**: `analysis-engine/app/main.py` (FastAPI app on port 8001). Provides APIs for triggering analysis tasks synchronously and asynchronously.
*   **Laya Decision Engine**: Bootstrapped via `deploy/docker/Dockerfile.laya` (Port 8005).

## 3. Service Boundaries and Relationships
*   **Frontend ↔ Backend**: The frontend communicates exclusively with the backend via the `/api/v1` REST API using JWT Bearer authentication.
*   **Backend ↔ Analysis Engine**: The backend acts as a gateway. It places the target APK in storage, queues a job, and delegates execution to the Analysis Engine over an internal Compose network (`http://analysis-engine:8001`). This connection is authenticated via an `ANALYSIS_ENGINE_INTERNAL_TOKEN`.
*   **Analysis Engine ↔ External Services**:
    *   **MobSF**: Orchestrates static vulnerability analysis to the MobSF container (`http://mobsf:8000`).
    *   **Mitmproxy**: Reads HAR network captures generated by the mitmproxy sidecar (`mitmproxy:8080`) from a shared volume.
    *   **Laya**: Connects to the local Laya service (`http://laya:8000` / port `8005`) for rapid System-1 UI navigation decisions during dynamic exploration.
    *   **Threat Intel APIs**: Calls external APIs (Gemini, VirusTotal, OTX, AbuseIPDB).

## 4. DAE (Dynamic Analysis Engine) Dependencies
*   The DAE runs within the `analysis-engine` container.
*   Communicates with the Android Emulator (Genymotion/AVD) via **ADB** (typically `host.docker.internal:5037` or direct TCP).
*   Utilizes **Frida** (`17.16.4`) to hook into processes dynamically. Pre-compiled hook payloads are injected to trace and control the application.
*   The dynamic sandbox logic is contained in `shared/sudarshan_core/engines/frida_sandbox.py` and employs the Agentic Explorer (`agentic_explorer.py`).

## 5. VIDE (Visual Impersonation Detection Engine) Dependencies
*   Reads the banking baseline corpus stored in the `VIDE/` directory (mounted read-only).
*   Compares extracted UI layouts (from APKTool) or dynamically captured UI hierarchies against the `baselines_index.json` registry and structural fingerprints.
*   The Backend worker pool refreshes its cache of the corpus, while the Analysis Engine uses it at runtime to detect visual spoofing.

## 6. Storage and Database Dependencies
*   **Relational Database**: Managed by `backend/app/db/database.py`. Supports both **SQLite** (legacy/default, stored in `dbdata` volume) and **PostgreSQL** (production, stored in `pgdata` volume). It maintains users, cases, async job status, enterprise batches, and a 24-hour IOC cache.
*   **Artifact Storage**: Implemented in `shared/sudarshan_core/storage/artifact_storage.py`. It supports local filesystem storage (`/app/uploads` volume) and GCS. Both backend and analysis engine use it for zero-copy file sharing of APKs and evidence artifacts (like generated manifests, screenshots, dynamic logs).

## 7. Docker and Deployment Dependencies
*   Orchestrated via `docker-compose.yml`.
*   **Services**: `frontend`, `backend`, `analysis-engine`, `mitmproxy`, `mobsf`, `postgres`, `laya`.
*   **Volumes**: 
    *   `uploads`: Zero-copy artifact sharing.
    *   `mitmproxy_har`: HAR file drop zone between mitmproxy and analysis engine.
    *   `dbdata`: SQLite database persistence.
    *   `pgdata`: PostgreSQL data persistence.
    *   `laya_model_cache`: Local cache for HuggingFace Laya model weights.
*   **Shared Core**: Mounted directly into `backend` and `analysis-engine` containers using `PYTHONPATH=/app:/opt/sudarshan-core`.

## 8. Runtime Execution Paths
The end-to-end execution path for an APK analysis:
1.  **Ingestion**: An analyst uploads an APK via the Frontend to the Gateway (`backend`).
2.  **Storage & Queueing**: The Backend saves the file via `ArtifactStorage` and enqueues an analysis job.
3.  **Dispatch**: The Backend worker polls the queue and triggers the `analysis-engine` asynchronously.
4.  **Static Pipeline**: The Analysis Engine executes Androguard, APKTool, JADX, and MobSF concurrently.
5.  **Manifest Generation**: A dynamic investigation manifest is constructed based on static findings.
6.  **Dynamic Sandbox (DAE)**: The sandbox attaches via ADB and Frida, injecting hooks. The Agentic Explorer employs Laya for fast navigation and Gemini for complex reasoning to explore the UI.
7.  **Telemetry & Network**: mitmproxy flows and execution events are ingested.
8.  **Scoring & Synthesis**: Threat intelligence is correlated, VIDE impersonation checks are executed, and deterministic risk scores (STEI, BFCI) are calculated.
9.  **Finalization**: The Analysis Engine pushes generated artifacts back to `ArtifactStorage` and returns a structured JSON report to the Backend.
10. **Persistence**: The Backend persists the summarized metadata and the raw JSON report in the database.
